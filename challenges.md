# Engineering Challenges & Technical Post-Mortem

This document records the actual technical challenges encountered during the development of the **INE Product Price Tracker**, their root causes, the engineering solutions applied, and their verification.

---

## Challenge 1: Anti-Bot Challenge Attestation Rejection (HTTP 401) via Local Clock Drift

### Symptom
- Running `npm run scrape -- --ids 200` failed with:
  ```
  [REQ] POST https://demo.inelabteamdev.com/api/session
  [RES] 401 https://demo.inelabteamdev.com/api/session
  [RES BODY] {"error":"unauthorized"}
  product 200 attempt 1/4 → GATE_NOT_PASSED: Store showed error: "Couldn't load the price after 1 attempts. challenge_failed TRY AGAIN"
  ```

### Root Cause Investigation
1. Reverse-engineering the store's client bundle (`/assets/index-B9UiQq4X.js`) revealed that the store requires interactive mouse telemetry, WebAssembly proof-of-work computation, and client environment attestation.
2. The attestation payload generated by `cr(e)` packages browser telemetry:
   ```javascript
   {
     env: {
       canvas: ar(),
       gl: or(),
       hc: navigator.hardwareConcurrency || 1,
       scr: [screen.width, screen.height, window.devicePixelRatio || 1],
       frames: t,
       at: Date.now() // <--- Attestation timestamp
     },
     ix: { hoverAt, dwellMs, moves, clickAt: Date.now(), trusted: true }
   }
   ```
3. Checking the developer system clock vs the store server's HTTP `Date` header revealed:
   - System time: `Sun Sep 20 05:23:26 PM UTC 2026` (`17:23:26 UTC`)
   - Store server header: `Sun, 20 Sep 2026 11:55:55 GMT` (`11:55:55 UTC`)
   - The local machine's system clock was skewed **5 hours 27 minutes into the future** relative to the live server.
4. When the browser ran `Date.now()`, it produced a timestamp ~19,650,000 ms ahead of the server's challenge timestamp `ts`. The store backend rejected the future-dated attestation as unauthorized (`401 {"error":"unauthorized"}`).

### Solution
- Added `getStoreTimeOffset()` in `backend/src/store/browserPool.js` to dynamically query the store's server timestamp (`GET /api/challenge`) and calculate `timeOffset = serverData.ts - Date.now()`.
- Injected an init script into each Playwright `BrowserContext` to synchronize the browser's `Date.now` with the store server:
  ```javascript
  const offset = timeOffset;
  if (offset !== 0) {
    const origNow = Date.now;
    Date.now = function() {
      return origNow.call(Date) + offset;
    };
  }
  ```
- Updated Validation Gate V9 (`checkV9Freshness` in `validate.js`) to evaluate freshness relative to `Date.now() + timeOffset`.

### Verification
- `POST /api/session` returned `200 OK` with session token.
- Challenge passed on attempt 1/4 and real price loaded cleanly.

## Challenge 2: Split-Span Price Digits Triggering False Divergence (`PRICE_AMBIGUOUS`)

### Symptom
- Price extraction failed with:
  ```
  product 200 attempt 1/4 → PRICE_AMBIGUOUS: Authoritative quote (973600) and divergent DOM prices (900, 700, 300, 600)
  ```

### Root Cause Investigation
1. The store deliberately splits formatted price strings into individual single-character `<span>` tags with zero-width characters (e.g. `<span>9</span><span>,</span><span>7</span>...`).
2. The scraper's initial candidate extraction queried `.price-block *` and required `el.children.length === 0` to select leaf text nodes.
3. This condition caused the parent container containing the full price (`₹9,736`) to be excluded because it had child `<span>` elements, while the individual digit spans (`"9"`, `"7"`, `"3"`, `"6"`) were collected as candidates.
4. `parsePrice()` then parsed each digit as an independent price (`900`, `700`, `300`, `600` paise), creating conflicting candidates that triggered Validation Gate V5 (`PRICE_AMBIGUOUS`) against the real quote of `973600` paise.

### Solution
- Updated `priceScraper.js` to collect `isPriceContainer` elements—elements that contain currency symbols (`₹`, `Rs`, etc.) whose children are inline formatting spans (`SPAN`, `B`, `STRONG`, `I`, `EM`).
- In `pickPrice.js`, ignored isolated numeric strings `<= 3` characters without currency symbols.
- Added a fallback cross-check against lines in `blockText` before flagging divergence.

### Verification
- Re-running `npm run scrape -- --ids 200` accurately extracted `9736 INR` (`cross_checked=true`), matching both DOM and decrypted quote.

## Challenge 3: Invariant I6 Violation on Unclean Process Termination

### Symptom
- When a scrape process was aborted (`SIGKILL` or interrupted between retry loops), `npm run verify:db` failed with:
  ```
  ✗ [I6] FAIL: Retried attempts are never left dangling as final attempt (1 violations)
  ```

### Root Cause Investigation
- During multi-attempt retry cycles, intermediate attempts are saved with `outcome = 'retried'`.
- If the Node process terminates abruptly before attempt `N + 1` can be recorded, the last attempt for that product remains `outcome = 'retried'`, violating Invariant I6 ("A retried attempt is never the final attempt for that product in that run").

### Solution
- Created SQL migration `0003_sweep_stale_fix.sql` / `0004_fix_sweep_ambiguous.sql` updating `sweep_stale()`:
  ```sql
  update scrape_attempts a
  set outcome = 'failed',
      finished_at = coalesce(a.finished_at, now()),
      error_code = coalesce(a.error_code, 'INTERRUPTED'),
      error_message = coalesce(a.error_message || ' (run interrupted before retry)', 'Run interrupted before retry')
  from scrape_runs r
  where a.run_id = r.id
    and a.outcome = 'retried'
    and r.status in ('interrupted', 'aborted', 'completed', 'completed_with_failures')
    and a.attempt_number = (
      select max(a2.attempt_number)
      from scrape_attempts a2
      where a2.run_id = a.run_id and a2.tracked_product_id = a.tracked_product_id
    );
  ```
- Any terminal `retried` attempt on an interrupted or completed run is converted to `failed` with error code `INTERRUPTED`.

### Verification
- Calling `sweep_stale()` resolved the dangling attempt, and `npm run verify:db` passed all 7 invariants.

## Challenge 4: Intentional Anti-Bot Cookie Banner Interception

### Symptom
- Headless interactions timed out clicking "Reveal price":
  ```
  elementHandle.click: Timeout 30000ms exceeded.
  <div class="cookie-overlay">...</div> intercepts pointer events
  ```

### Root Cause Investigation
- The store injects a dynamic modal `<div class="cookie-overlay">` covering the entire viewport with ~25% probability.
- Decompiling the client bundle revealed an intentional chaotic counter `Jr()` that requires 1, 2, or 3 clicks on the Accept button before dismissing the overlay.

### Solution
- Implemented `dismissCookies(page)` which inspects the DOM for `.cookie-overlay` and clicks `button[aria-label="Accept cookies"]` in a loop with a small dwell until the overlay element is completely detached from the DOM.
- Called `dismissCookies()` prior to hovering, before clicking reveal, and prior to DOM inspection.

### Verification
- Scrapes cleanly bypassed the cookie overlay across 100% of tested runs.

## Challenge 5: Database Foreign Key Constraint vs Numeric Product ID in CLI

### Symptom
- Running `npm run scrape -- --ids 200 --persist` threw a Postgres foreign key error:
  ```
  invalid input syntax for type uuid: "200"
  ```

### Root Cause Investigation
- The CLI accepts user-friendly store product numeric IDs (e.g. `200`, `114`).
- However, the `scrape_attempts` table schema specifies:
  ```sql
  tracked_product_id uuid not null references tracked_products(id)
  ```
- The CLI was passing the string `"200"` directly to `createAttempt`, expecting an auto-coercion that Postgres UUID types reject.

### Solution
- In `backend/src/cli/scrape.js`, added pre-resolution logic: before starting a persisted run, the CLI checks `tracked_products` for `store_product_id = '200'`. If not yet tracked, it auto-registers/upserts the product and passes the resulting UUID `id` to the run orchestrator.

### Verification
- CLI runs with `--persist` seamlessly resolve UUIDs and insert attempts without schema errors.

## Challenge 6: camelCase Payload Causing Null Constraint Failure on `observed_at`

### Symptom
- Persisting a successful observation triggered:
  ```
  RPC finish_attempt_success failed: null value in column "observed_at" of relation "price_observations" violates not-null constraint (23502)
  ```

### Root Cause Investigation
- The JavaScript extractor produced observation objects using camelCase naming (`observedAt`, `priceMinor`, `stockState`).
- The PostgreSQL RPC `finish_attempt_success` extracted values using `p_observation->>'observed_at'`, which evaluated to NULL, violating the NOT NULL constraint on `price_observations.observed_at`.

### Solution
- In `backend/src/db/repo.js`, explicitly mapped observation objects to `snake_case` prior to dispatching RPC calls.
- Deployed migration `0005_fix_finish_attempt_success.sql` updating the RPC function to use `coalesce(p_observation->>'observed_at', p_observation->>'observedAt')` for all fields, ensuring zero failures regardless of casing convention.

### Verification
- Both product 200 and product 114 persisted observations directly to Supabase with 100% data integrity and zero constraint violations.
